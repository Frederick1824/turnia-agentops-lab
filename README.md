# TurnIA AgentOps Lab

> A small, traceable AgentOps experiment built on a real appointment scheduling application.

[🇪🇸 Leer en español](./README.es.md)

---

## Overview

**TurnIA AgentOps Lab** is an experimental repository created to explore how AI coding agents can be used with explicit contracts, limited authority, adversarial review, executable evidence, and human-controlled decision making.

The experiment was performed on **TurnIA**, an existing appointment scheduling application built with React, Vite, TypeScript and local persistence.

The objective was not to rebuild TurnIA or maximize automation.

The objective was to answer a narrower question:

> Can an AI-assisted development workflow identify, demonstrate, fix and verify a real defect while preserving traceability and human authority?

The first experiment, `EXP-001`, successfully completed that cycle.

---

## Core idea

The workflow follows a simple AgentOps principle:

```text
Autonomy ≠ Authority
```

Agents can inspect, propose, implement and test.

Humans retain authority over:

* scope;
* contracts;
* dependencies;
* production changes;
* progression between phases;
* acceptance of evidence;
* commits and publication;
* experiment closure.

This separation was deliberately enforced throughout the experiment.

# EXP-001

## Reservation validation

The first experiment focused on one business rule:

> An appointment must not be accepted if its requested time does not belong to one of the valid time slots generated by the business configuration.

Example configuration:

```text
Opening:       10:00
Closing:       19:00
Slot duration: 30 minutes
Capacity:      3
```

Adversarial input:

```text
Date: 2026-08-17
Time: 03:00
Slot: 1
```

Expected result:

```text
Rejected
```

Initial implementation behavior:

```text
Accepted
```

---

## Agent topology

The experiment used three roles:

```text
Planner
   ↓
Executor
   ↓
Critic
```

### Planner

Responsible for defining:

* scope;
* contracts;
* acceptance criteria;
* exclusions;
* implementation boundaries.

The Planner cannot modify production code or approve its own work.

### Executor

Responsible for:

* implementing explicitly authorized changes;
* performing minimal refactors;
* running builds and tests;
* preserving the approved scope.

The Executor cannot expand requirements on its own.

### Critic

Responsible for trying to disprove that the implementation satisfies the contract.

The Critic analyzes the system through adversarial dimensions such as:

* assumptions;
* boundaries;
* trust;
* dependencies;
* time and ordering;
* threats.

A finding is not considered demonstrated until executable evidence exists.

Commit:


The Critic discovered that valid time slots were generated correctly for the UI, but the reservation operation did not independently verify that the submitted time belonged to those slots.

The finding was registered as:


## 4. Executable evidence

Commit:

```text
6a7b8d8
test: demonstrate EXP-001-F01 with adversarial evidence
```

The existing reservation guards were mechanically extracted into a pure domain function without fixing the suspected defect.

Vitest was then introduced.

Four characterization tests passed.

The adversarial test failed:

```text
Test Files  1 failed (1)
Tests       1 failed | 4 passed (5)
```

Failure:

```text

```

The implementation considered a reservation at `03:00` valid.

At this point:

```text
EXP-001-F01 → Demonstrated
```

The red test was not considered a failed experiment.

It was the first executable evidence that the Critic's hypothesis was correct.

Commit:


The domain validation was changed to reuse the existing `generateTimeSlots` logic.

The requested time must now belong to the configured slot set.

No hardcoded timetable was introduced.

The original adversarial assertion was not modified.

# What EXP-001 does NOT prove

EXP-001 demonstrates and fixes one specific finding.

It does **not** claim that TurnIA is exhaustively tested.

Areas outside the experiment include:

* multi-tab concurrency;
* malformed persisted data;
* authentication;
* server-side security;
* backend persistence;
* complete appointment lifecycle validation;
* every boundary defined in the reservation contract;
* npm dependency vulnerabilities.

Those areas may become future experiments, but they are not silently treated as solved.

# Key lessons

### Static inspection is not proof

A plausible bug remained a hypothesis until executable evidence reproduced it.

### FAIL before FIX matters

Correcting the problem before demonstrating it would have destroyed useful evidence.

### The same test before and after is stronger evidence

The adversarial assertion was not weakened to produce a green result.

Production behavior changed instead.

### Contracts reduce agent drift

Explicit scope prevented unrelated refactors and fixes from entering the experiment.

### Critics need evidence

The Critic was useful because it produced a refutable claim rather than a vague code-review opinion.

### More agents are not automatically better

For this experiment:

```text
Planner → Executor → Critic
```

was sufficient.

Adding more roles would have increased coordination cost without clear value.

### Governance has a cost

For a small functional fix, the documentation and handoffs were intentionally heavier than conventional development.

That overhead only makes sense when traceability, experimentation or risk justify it.
